# Design decisions

One short paragraph each. Newest decisions last.

**1. Framework-free core, thin FastAPI shell.** Everything that matters (limiter, breaker, cache, router, scheduler, ledger, gateway pipeline) is plain Python/asyncio with dataclasses. FastAPI only translates HTTP to `Gateway.handle()`/`handle_stream()`. This made the core fully testable with the standard library, and it is why the HTTP layer is the only part not exercised in the build sandbox (no FastAPI installed, no network). Pydantic/pydantic-settings were therefore *not* used: request validation is hand-written in `ChatRequest.from_openai`, and settings are a dataclass read from env vars.

**2. Priority = reserved capacity + guaranteed shares (not weighted fair queuing).** Each lane has a *floor* (fraction of the bucket that must remain after it takes tokens): interactive 0, normal 0.15, batch 0.35, bulk 0.50. Reserved capacity is O(1), needs no queue state (so it ports directly to one Redis Lua script) and is easy to reason about: interactive can always burst into the capacity batch is not allowed to touch. The weakness of pure reservation is starvation, so low lanes also own a small *guaranteed* sub-bucket (normal 10 %, batch 10 %, bulk 5 % of the refill rate) which interactive cannot consume. Cost of this choice: interactive's burst is `1 - 0.25 = 75 %` of bucket capacity even when no batch work exists (the guaranteed tokens are held back). WFQ would avoid that idle waste but needs per-lane queues and virtual-time bookkeeping across processes.

**3. Window guarantee instead of a plain bucket.** A token bucket with capacity = limit and rate = limit/60 can admit ~2x the limit in a 60 s window. We set `capacity = 10 % of limit` and `rate = (limit - capacity)/60`, so *any* 60 s window admits at most `capacity + rate*60 = limit`. This is tested with a sliding-window assertion. Cost: ~10 % lower sustained throughput and smaller bursts. Token (TPM) limits use a minimum capacity of 2,048 tokens; a request larger than the capacity is clamped to the capacity for admission purposes.

**4. Estimated tokens are reserved up front, not refunded.** The limiter is charged `prompt_estimate + (max_tokens or 256)` before the call. We do not refund the unused part, so TPM admission is conservative (safe against 429s, slightly under-utilised).

**5. SQLite (WAL) instead of Postgres + SQLAlchemy/Alembic.** Ledger, API keys, jobs and the durable task queue live in one SQLite file via stdlib `sqlite3` with a single `schema_version` row. WAL + `BEGIN IMMEDIATE` lets several worker *processes* share it (the SIGKILL recovery test does exactly that). This keeps lite mode and the full mode identical and dependency-free. Postgres/pgvector and a Redis-backed queue are on the roadmap; they are **not implemented**. Calls are synchronous but sub-millisecond; at very high task rates they should move to a thread pool or a server DB.

**6. Redis is used only for the rate limiter (Lua) in this version.** The Lua script mirrors the unit-tested Python algorithm and uses Redis `TIME` as the single clock so multiple gateway nodes share one timeline. It was not executed against a live Redis in the build sandbox.

**7. Lease-based queue with fencing.** `claim` moves tasks to `leased` with an expiry; every outcome (`complete/retry/release/dead`) is fenced on `owner` and `status='leased'`, so a zombie worker's late result is ignored. Each claim increments `attempts` so a task that keeps crashing workers is dead-lettered. Deferrals and shutdown releases *restore* the attempt. Exactly-once *charging* comes from `usage.task_key UNIQUE` (`INSERT OR IGNORE`); a crashed-and-retried task may call the provider twice, but is billed once.

**8. Queue-level aging.** Claim order is `available_at + rank*30 s`, so a bulk task is "~90 s older" than a batch one at most; bulk cannot starve forever behind a steady stream of higher lanes.

**9. Cache is in-process.** Exact + semantic layers live in memory (numpy matrix per namespace). They are lost on restart and not shared between API replicas. Redis/pgvector backends are roadmap items. Single-flight coalescing makes concurrent identical requests share one upstream call.

**10. Semantic layer safety guard.** Embeddings treat "capital of France" and "capital of Spain" as near-identical. Semantic hits therefore also require the sets of numbers and proper nouns to match (`CACHE_GUARD`, default on), only fire for single-turn prompts, and are namespaced by model family + system prompt + tools + response format. The measured effect is in `BENCHMARKS.md`.

**11. The semantic layer is OFF with the fallback embedder (measured, not assumed).** Without `sentence-transformers` the cache uses a hashed n-gram embedder. Two studies (`BENCHMARKS.md` section 3) show it is unusable for semantic matching: pairwise, it scores near-misses *above* paraphrases; replayed through the real cache with nearest-neighbour search over the whole workload, it produced ~0 correct paraphrase hits and **5.5 % wrong answers at the old default (0.92 + guard)**. `CACHE_SEMANTIC=auto` (default) therefore enables the semantic layer only when a real embedding model is loaded; exact-match caching and single-flight always work. `CACHE_SEMANTIC=on` forces it (the benchmark keeps one such run as a documented counter-example). Install the `embeddings` extra and re-run `eval_cache_threshold.py --embedder auto` and `eval_cache_index.py --embedder auto` to choose a threshold for `BAAI/bge-small-en-v1.5`; that was not possible offline.

**12. Substitution of unavailable models.** If a client asks for `gpt-4o` but no OpenAI key is configured, the gateway serves it from an enabled model of the same tier (`ALLOW_SUBSTITUTION=true`, visible in `X-Model`/`X-Provider`). This is what makes "use OpenAI-, Groq- and Gemini-model names through one endpoint, for free" work. Set it to `false` for strict behaviour.

**13. Breaker semantics.** 5xx/timeouts/auth errors count as failures; provider 429s do *not* (the provider is alive; our configured limit is just too generous) but are counted in `provider_429_total`. Client errors (400) are never failed over. A half-open breaker admits one probe.

**14. Dashboard is a static page, not Next.js.** `/dashboard` is a single HTML file polling `/admin/stats`. It needs no build step and ships in the wheel. It has not been viewed in a browser in the build sandbox.

**15. Streaming failover limits.** Failover is possible only before the first chunk. A mid-stream upstream failure is surfaced in-band as an SSE error event followed by `[DONE]`; the partial response is recorded as `stream_error` and never cached. Cost headers are omitted on streams (cost is only known at the end) but the ledger records it.
